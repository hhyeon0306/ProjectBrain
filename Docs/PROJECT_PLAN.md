# Project Brain — 개발 계획

작성일: 2026-09-04 · 상태: 기획 확정 전, Unity 프로젝트 생성 단계

## 1. 목적

Unity 프로젝트의 코드 구조와 설계 의도를 사람과 AI가 함께 관리하고, 코드 변경 이후 필요한 문서 검토와 검증을 작업 완료 조건으로 연결하는 개발 도구를 만든다.

넥토리얼 지원용으로 실행 가능한 작은 완성작과 실제 개발·검증 기록을 남긴다. 기존 Unity 클라이언트 포트폴리오는 실제 적용 사례로 활용한다. 지원 마감은 2026-09-07 오후 4시이며, 새 기능보다 제출 가능한 결과물 확보를 우선한다.

## 2. 핵심 사용 흐름

1. 사람이 대상 스크립트와 변경 목적을 선택한다.
2. AI가 MCP 도구 `begin`으로 작업을 등록하고 관련 맥락을 받는다.
3. AI 또는 사람이 기존 에디터에서 코드를 수정한다.
4. `status`가 실제 변경과 문서의 오래됨을 표시한다.
5. 문서 검토 후 `verify`가 실제 검증 결과를 기록한다.
6. `complete`가 현재 코드에 유효한 문서 확인과 검증 결과를 검사한다. 조건이 부족하면 이유와 다음 행동을 반환한다.
7. Unity UI에서도 같은 작업 상태와 결과를 확인한다.

시연의 핵심은 ‘수정 후 완료 요청 거절 → 문서·검증 보완 → 완료 성공’이다.

## 3. 범위와 우선순위

### 반드시 완성할 MVP

- 명시한 폴더 안의 C# 스크립트 목록과 안정적인 식별자.
- 노드별 역할, 설계 의도, 주의사항, 문서 확인 당시 코드 해시.
- 소수 노드의 그래프, 선택 노드의 문서 패널, 검토 필요 표시.
- 선택 노드와 제한된 연결 범위의 Markdown 맥락 내보내기.
- `begin`, `status`, `verify`, `complete` MCP 작업 흐름.
- 현재 코드와 검증 대상 코드가 다르면 완료를 거절하는 상태 검사.
- 작은 Unity 예제에서 성공 사례와 거절 사례 시연.

### 시간이 남으면

- 기존 클라이언트 포폴의 별도 브랜치에 패키지 적용.
- CI용 독립 CLI 어댑터 (이번 MVP에서는 구현하지 않음).
- 자동 참조 추출 범위 확장, 그래프 탐색 편의 개선.

### 이번 범위에서 제외

- 채팅 UI, LLM API 자체 연동, 자동 장기 기억, 벡터 DB.
- 모든 C# 의미 관계의 완전한 분석, 자동 설계 의도 생성.
- 전체 프로젝트 자동 리팩터링, 화려한 그래프 효과.
- 커밋·병합 차단, CI 설치, 외부 배포, 새로운 영상 제작.

참조 자동 추출이 일정에 부담되면 수동 관계 등록으로 축소하고 출처를 명시한다. 문자열 검색 결과를 정확한 의미 분석 결과로 표현하지 않는다.

## 4. 구조

```text
사람 → Unity Editor UI ─┐
                       ├→ 공통 도메인 규칙 → 문서·작업 상태
AI → 로컬 MCP(stdio) → Unity 연결 계층 ┘    → Unity 검증 실행
```

- 별도 Unity 프로젝트에서 개발한다. 기존 포폴과의 버전 일치는 적용 전에 확인한다.
- 툴 코드는 로컬 UPM 패키지 `Packages/com.projectbrain.editor`로 분리하는 것을 기본안으로 한다.
- 예제 게임 코드는 `Assets/ProjectBrainDemo`에 둔다.
- 메타데이터와 문서는 프로젝트 루트 `.projectbrain/`에 둔다. 사람이 관리할 자료와 재생성 가능한 실행 결과를 구분한다.
- Unity UI와 MCP는 완료 판단 규칙을 공유한다. 두 곳에 같은 상태 변경 로직을 따로 만들지 않는다.
- Codex 연결은 로컬 stdio MCP 서버로 확정한다. 외부 프로세스에서 MCP 연결을 유지하고 Unity와 요청·응답을 교환한다. 런타임은 설치 환경 확인 후 결정한다. Unity 미실행·재컴파일·응답 지연을 상태로 구분하며 검증 성공으로 처리하지 않는다.
- 결정 근거는 `INTERFACE_DECISION.md`를 참조한다. 독립 CLI를 먼저 만들거나 CLI와 MCP를 동시에 구현하지 않는다.

## 5. 데이터와 강제성

### 최소 데이터

| 데이터 | 필수 내용 |
|---|---|
| 노드 | ID, 파일 경로, 현재 해시, 역할·설계 문서, 문서 확인 해시 |
| 관계 | 시작·끝 ID, 관계 종류, 수동/자동 출처 |
| 작업 | ID, 목적, 대상 노드, 시작 스냅샷, 실제 변경, 상태 |
| 검증 | 작업 ID, 검증 종류, 대상 스냅샷, 성공/실패, 로그 경로 |

경로 변경에 대비해 가능한 경우 Unity GUID를 노드 ID로 사용한다. 코드에서 추출한 사실, AI 제안, 사람이 확인한 설계 의도를 구분한다.

### 완료 규칙

- 등록되지 않은 외부 변경도 다음 검사에서 탐지한다.
- 작업 범위를 벗어난 변경은 숨기지 않고 범위 재확인을 요구한다.
- 코드 해시가 문서 확인 해시와 다르면 문서 재검토가 필요하다.
- AI가 쓴 ‘통과’ 문장은 검증 증거로 인정하지 않는다. 검증 실행기가 수집한 결과를 사용한다.
- 검증 이후 관련 코드가 달라지면 검증 결과를 무효화한다. MVP에서는 감시 대상 전체 스냅샷으로 보수적으로 검사한다.
- 컴파일 성공과 동작 검증을 구분한다. 필요한 테스트가 실행되지 않았다면 성공으로 처리하지 않는다.
- 사람의 확인이 필요한 항목은 Unity UI에서 별도로 확인한다. MCP 호출만으로 사람의 승인을 대신하지 않는다.
- 문서 내용의 정확성과 코드의 완전한 무결성을 해시만으로 보장한다고 주장하지 않는다.

이 도구의 강제성은 ‘Project Brain 작업 완료’에 적용된다. 로컬 파일 직접 수정이나 툴 자체 우회까지 막는 보안 경계는 아니다. 실제 병합 강제는 추후 보호된 CI 검사와 연결해야 한다.

## 6. 구현 순서와 일정

시간은 목표 배분이며, 환경 확인 후 조정한다. 한 단계가 끝날 때 실행 가능한 상태를 남긴다.

| 단계 | 목표 | 완료 기준 |
|---|---|---|
| 1. 환경·골격 | 버전, 컴파일, 패키지 경계 확인 | 빈 Editor 창과 작은 예제가 정상 동작 |
| 2. 작업 규칙 | 노드·문서·해시·완료 조건 구현 | 오래된 문서와 검증 결과로 완료 불가 |
| 3. MCP 연결 | 제한된 도구와 맥락 조회 | Codex에서 실제 MCP로 작업 시작부터 완료까지 실행 |
| 4. UI | 목록·간단한 그래프·문서 패널 | 같은 작업 상태를 사람도 확인 가능 |
| 5. 적용·증거 | 예제 검증, 가능하면 기존 포폴 일부 적용 | 성공·실패 로그와 스크린샷 확보 |
| 6. 제출 정리 | README와 포폴 설명 | 목적·구조·판단·검증·한계를 설명 가능 |

- 9/4: 환경 확인, 골격과 작업 규칙 우선.
- 9/5: MCP를 포함한 전체 흐름 완성 목표. 이후 새 기능보다 안정화 우선.
- 9/6: 적용 사례와 문서 정리. 기존 PPT 및 지원서 작업 시간 확보.
- 9/7: 제출 파일·링크 최종 확인과 여유 있는 제출. 새 기능 착수 금지.

일정이 밀리면 자동 관계 분석 → 그래프 꾸미기 순서로 제외한다. 작업 상태, 변경 감지, 완료 조건, 검증 증거는 유지한다.

## 7. 토큰과 작업 시간 운영 원칙

- 이 계획을 설계 기준으로 사용하고, 세션 인수인계는 `PROGRESS.md` 한 파일에 짧게 남긴다.
- 매 작업은 목표 하나와 완료 기준 하나로 시작한다. 필요 파일과 직접 의존성만 읽는다.
- `Library`, `Temp`, `Logs`, 생성된 프로젝트 파일과 전체 소스를 기본 맥락에 넣지 않는다.
- AI 맥락 출력은 기본 연결 1단계, 파일·문서 수 및 출력량 제한을 둔다. 잘린 항목은 목록으로 알린다.
- 파일 경로·해시·짧은 요약을 먼저 제공하고 본문은 필요할 때 요청한다.
- 전체 문서를 반복 생성하지 않고 변경된 항목만 수정한다.
- 구현 전에 긴 대안 조사나 추상화를 하지 않는다. 결정이 필요한 부분만 짧게 비교한다.
- 테스트는 해시 무효화, 완료 거절, 실제 MCP 연결 등 핵심 위험에 집중한다. 단순 UI마다 별도 테스트를 만들지 않는다.
- 검증된 단계는 반복 검사하지 않는다. 관련 코드 변경이나 명확한 실패 위험이 있을 때만 다시 검사한다.
- 자동 하위 에이전트 사용 없이 진행한다. 진행 보고는 완료 내용·다음 작업·막힌 점 중심으로 짧게 한다.

## 8. 평가와 포트폴리오 자료

실제 실행으로 아래 사례를 기록한다.

1. 작업 외부에서 코드를 수정하면 검토 필요 상태가 되는가?
2. 검증을 실행하지 않고 완료하면 거절되는가?
3. 검증 이후 다시 수정하면 이전 결과가 무효화되는가?
4. 문서 검토와 필요한 검증을 마치면 완료되는가?
5. 같은 코드 변경 작업에서 제한된 맥락이 필요한 정보를 포함하는가?

입력량 비교는 전체 문서 대비 선택 맥락의 문자 수 또는 측정 가능한 토큰 수를 기록한다. 토큰 추정치는 추정이라고 표시한다. 시간 절감이나 품질 향상은 실제 비교 전에는 가설로만 설명한다.

최종 자료는 실행 방법, 구조 그림, 위 사례의 로그·스크린샷, 본인의 판단과 AI의 기여, 알려진 한계를 포함한다. 공고가 요구하는 코드 작성·검증 역량을 구체적 사례로 설명하되 채용 평가 결과를 보장한다고 표현하지 않는다.
